## 2. Separation: Product-Enabling Runtime Qualification vs. Optional R&D

A core risk in early ML-backed products is conflating **engineering qualification of a vanilla local model** (required before Product Feature 2 can extract scanned maintenance paperwork) with **optional R&D optimization hypotheses** (`WP-0004`). They must remain strictly separated:

### 2.1 Product Feature 1 Needs Zero OCR

Durable intake (`DI-01` through `DI-08` in `02-PRODUCT-BRIEF.md`) stores and retrieves immutable PDF bytes, SHA-256 digests, byte lengths, and an honest `awaiting-extraction` state in PostgreSQL. Neither `Unlimited-OCR-2` nor any Python worker is in its critical path.

### 2.2 Product-Enabling Qualification Gates (Required Before Any GPU Run or Feature 2)

Before any local OCR baseline is claimed—and before any `WP-0004` GPU experiment executes—a bounded runtime-qualification assignment must clear five concrete platform, storage, security, and licensing gates uncovered by our source inspection:

1. **Storage & Cache Placement Gate (`C:` has only `65.70 GiB` free):**
   - Raw weights are `6.23 GiB`, but Hugging Face's symlink/blob cache, a dedicated Python virtual environment with Windows CUDA PyTorch wheels (`~2.5–3.5 GiB`), and rasterized page intermediates require `~12–16 GiB` alongside PostgreSQL clusters, `.NET` build artifacts, and Angular `node_modules`.
   - Qualification must inventory any secondary local volume (or explicitly budget a bounded directory with `HF_HOME` pinned outside Git and outside `temp`), never writing into a shared mutable "latest model" path.
2. **Native Windows Runtime Path Selection (Reject Custom SGLang; Qualify Native `Transformers`):**
   - Upstream's SGLang stack requires an unreleased custom wheel (`sglang-0.5.20.dev13+g75b9b06b02`), official `sglang` has zero `win_amd64` wheels, and upstream's server configuration relies on Linux `/dev/shm` (`SGLANG_UOCR_SHM_WRAP_MODEL_DATA=1`) and Linux Triton/CUDA-graph assumptions. Standing up SGLang on native Windows is needless infrastructure risk for low-concurrency intranet intake.
   - Instead, qualify the native `Transformers` path (`UnlimitedOCRForCausalLM.infer` in `modeling_unlimitedocr.py`), pinning `transformers==4.52.1` explicitly because `_sparse_base_impl.py` imports private `transformers` 4.52 internals (`_prepare_4d_causal_attention_mask`, `LlamaAttention`) that are fragile under `transformers` 5.x (`5.23.0` is current on PyPI). Test whether an isolated `Python 3.12.10` venv succeeds or whether a scoped `Python 3.10` venv (`uv venv --python 3.10`) is required.
3. **Windows CUDA Wheel & Blackwell (`sm_120`) Execution Gate:**
   - Running upstream's `pip install torch==2.13.0` on Windows installs PyPI's `116.4 MiB` **CPU-only** wheel because PyPI `torch==2.13.0` gates `cuda-toolkit` and `triton` to `platform_system == "Linux"`. Qualification must explicitly select a Windows CUDA PyTorch wheel index supporting RTX 5070 Ti (`sm_120`) and verify `torch.cuda.is_available()` and `bfloat16` matmul execution.
4. **Triton-Free `_forward_dense` Parity & 16 GiB WDDM Memory Gate:**
   - Official `triton` has no `win_amd64` wheel. Although `modeling_unlimitedocr.py` / `dash_attention.py` gracefully catch `ImportError` on `triton` and fall back to pure-PyTorch chunked SDPA (`_forward_dense`, `q_chunk=2048`) for prefill and pure-PyTorch fp32 (`_decode_attend`) for decode, `_forward_dense` allocates explicit `[B, 1, 2048, S]` attention masks.
   - Under Windows WDDM (`16,303 MiB` total VRAM with `>1,155 MiB` already held by desktop/browser/IDE processes), exceeding physical VRAM silently pages into shared system RAM over PCIe rather than immediately raising OOM, collapsing throughput. Qualification must measure `torch.cuda.max_memory_reserved()`, wall-clock prefill/decode latency, and numerical sanity on 1-page and 3-page synthetic PDFs under an observed GPU lease.
5. **Code-Safety & License Hygiene Gate (`eval()` and `PyMuPDF` AGPL-3.0):**
   - **Code execution hazard:** `modeling_unlimitedocr.py` line 120 executes `cor_list = eval(ref_text[2])` on model-generated text inside `extract_coordinates_and_label`, which runs whenever `save_results=True`. Production and evaluation wrappers **must** call `infer(..., save_results=False)` and parse raw output exclusively with pure regex/stdlib post-processing (`utils/process_unlimitedOCR2.py` + typed schema parsers).
   - **Copyleft hazard:** Upstream's `README.md` uses `PyMuPDF` (`pymupdf==1.27.2.2`), which is dual-licensed under **GNU AGPL-3.0** or a paid Artifex commercial license. Replace `PyMuPDF` before qualification with permissively licensed `pypdfium2` (`Apache-2.0 / BSD-3-Clause`, prebuilt `win_amd64` wheel) for PDF-to-RGB rendering and `pypdf` (`BSD-3-Clause`) for deterministic PDF stream inspection.
   - **Output contract:** `Unlimited-OCR-2` emits `<PAGE><BLOCK>label[bbox]<FORK>...<table>...</table>`, not domain JSON. Deterministic post-processing from raw layout blocks into source-linked candidate fields/tables is part of baseline integration, not a speculative model modification.

### 2.3 Optional R&D Improvements (`WP-0004` Backlog)

Only **after** the vanilla qualification baseline above runs deterministically on local hardware—or in CPU-only standalone pre-checks that do not claim an OCR baseline—should optional treatments (such as born-digital text-layer routing, multi-page `crop_mode` selection, or conditional scan deskewing in [02-hypotheses.md](02-hypotheses.md)) be evaluated via paired comparisons. Product delivery of Feature 1 never waits on either qualification or R&D, and Feature 2 requires only the vanilla qualification gate plus a minimal extraction adapter, not R&D improvement success.
