# Sensitivity to native title markup

The frozen native adapter counted heading markup and coordinates as visible characters. Correcting the heading parse on the saved public development outputs changes the four-page decision. Windows is still faster, but exceeds corrected native CER by **1.25 percentage points** on that packet. The working limit is one point. On the dense packet, Windows also exceeds corrected native CER by **1.81 points**, alongside the previously observed cell deficit. Windows stays within budget on the short page. These results apply to the stored development outputs in both orders.

| Packet | Frozen native edits | Corrected native edits | Frozen Windows edits | Windows CER change against corrected native | Corrected native / Windows position-correct cells | Fastest within budget, frozen → sensitivity |
| --- | ---: | ---: | ---: | ---: | --- | --- |
| Short | 46 / 121 | 2 / 121 | 2 / 121 | 0.00 points | N/A | Windows → Windows |
| Dense | 48 / 496 | 5 / 496 | 14 / 496 | +1.81 points | 39 / 42 vs 35 / 42 | Native → native |
| Boundary | 135 / 320 | 3 / 320 | 7 / 320 | +1.25 points | 8 / 9 vs 8 / 9 | Windows → native |

Baidu documents the optional heading level between `title` and the bounding coordinates. The frozen adapter expected the block label immediately before the coordinates. Four level-one and one level-two headings per run therefore became ordinary visible text or attached to the preceding block. The sensitivity adapter recognizes a numeric level only inside a title block followed by four integer coordinates and its fork marker. It then uses the original adapter for the block text and PDF coordinates. All other projection rules are identical. The local upstream README snapshot has SHA-256 `3070bb2f2802a5b17ad48923caffa905e2a8ff62394330e8ab0ba05533490ad1`. [Baidu postprocessing grammar at the recorded source revision](https://github.com/baidu/Unlimited-OCR/blob/64e6f066023b305ab03860603a9cf358a8b70148/utils/README.md)

The restored headings added one source-linked span on short, one on dense and three on boundary. Exact source-line counts for native changed from 2 to 3 of 4, 4 to 5 of 6 and 5 to 8 of 10, respectively. The original and corrected native projections produced identical critical-error values, locations and flags. Short retained one unflagged error. Dense retained four, and Windows introduced four new critical failures plus four different wrong readings in those previously wrong positions. Boundary retained three, and Windows produced different wrong readings in two of those three positions. Neither score interpretation supports unattended use.

This is an untimed CPU rescore of the native originals from the two public author comparisons. It fits no parameter and uses the original Windows predictions and original independent scorer. All raw page hashes, raster/source identities, official predictions and full official score objects were verified before rescoring. Each native, each Windows and each comparison object remains available in its frozen run directory. No inference, wall-clock measurement or independent replay was performed here. The corrected-parser ranking uses the original measured elapsed times. The incremental serialization cost of this parser change has not been measured. [Frozen results](../development-results.md) · [Complete official and corrected counts by order](scores/summary.json)

Run `rescore.py PUBLIC_CUSTODY_DIR NEW_OUTPUT_DIR` with the Q0 interpreter, `-I -B`. The output directory must be new. The script reads only the named public development packets, source-bound raw pages, their scoring keys and digest-verified scorer. Per-run JSON files contain every corrected native page, full corrected score and side-by-side critical readings. Both AB and BA returned identical full sensitivity summaries.
