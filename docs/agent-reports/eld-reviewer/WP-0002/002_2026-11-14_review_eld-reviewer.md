### 1. Technical assessment by review domain

- **Seed, authority, and provenance (`WP-0001 / 001`, [AGENTS.md](../../../../AGENTS.md), [START_HERE.md](../../../../START_HERE.md))**: Sound. `35f6090a9b2e16c7645b56f34b104eb3126d5c90` is verified as a true parentless root commit with the exact 20 inventoried files. Six bootstrap-kit files match `manifest.json` SHA-256 and byte counts; `00-START-COORDINATOR.txt` (`9384` bytes, `162cc5c3653b6d277e68087c4d0e3f8d7b4d38089bacced12040c2054989baa1`) matches [kit-provenance.md](../../../coordination/kit-provenance.md) without falsifying `manifest.json`. - **Transaction atomicity and acknowledgement ([F1-durable-intake.md](../../../design/F1-durable-intake.md) L42-L57)**: Sound. Storing <=10 MiB originals in PostgreSQL `bytea` (`original_artifacts`) alongside `documents` and `processing_jobs` inside one explicit `Read Committed` transaction with `SET LOCAL synchronous_commit=on` (plus verified server `fsync=on`, `full_page_writes=on`, `synchronous_commit=on`) eliminates two-store orphan/recovery complexity for `F1` and guarantees `201 Created` is sent only after WAL flush and transaction commit. Power-loss vs application-restart claim boundaries are accurately stated.
- **UUID retry and concurrent conflict semantics ([F1-durable-intake.md](../../../design/F1-durable-intake.md) L19-L39, L52-L54)**: Sound. Separating business submission identity (`Idempotency-Key` canonical `D` non-empty UUID) from content identity (`sha256` + `byte_length` + exact `bytea` comparison) satisfies [02-PRODUCT-BRIEF.md](../../../inputs/bootstrap-kit/02-PRODUCT-BRIEF.md): identical PDFs under distinct keys create distinct documents (`201`), exact retries under the same key return `200` without fragile re-parsing under future rules, and differing bytes under the same key return `409`. Resolving concurrent same-key races via PostgreSQL's unique index on `documents.idempotency_key` (`SqlState 23505` on that exact constraint name only -> rollback -> fresh `DbContext` read -> byte comparison -> `200`/`409`) is race-safe under `Read Committed`: if the leading writer commits, the waiter catches `23505` and sees the committed row; if the leading writer rolls back, PostgreSQL wakes the waiter and lets its insert succeed.
- **Interrupted and uncertain submissions ([F1-durable-intake.md](../../../design/F1-durable-intake.md) L38, L58-L71)**: Mostly sound, subject to `SB-03`. Retaining one pending UUID in `sessionStorage` without persisting PDF bytes in Web Storage, preventing double-click key minting, and providing `GET /api/submissions/{idempotencyKey}` properly separates transport uncertainty from durable `awaiting_extraction` job status. However, `5xx` server responses must also trigger the UI's `Submission outcome unknown` reconciliation state (`SB-03`).
- **Strict PDF admission limits ([F1-durable-intake.md](../../../design/F1-durable-intake.md) L28-L41)**: Bounded framing (`10 MiB`, `50` pages, raw `application/pdf`, `identity`/no content encoding, concurrency cap `2 -> 429`, server-generated download name `document-{documentId}.pdf` with `X-Content-Type-Options: nosniff`, explicit disclaimer against untrusted/hostile uploads) is strong. - **Test mechanisms ([F1-durable-intake.md](../../../design/F1-durable-intake.md) L112-L130)**: Sound. Using a separate PostgreSQL lock-holding connection (`DI-05`) and a local loopback response-dropping proxy (`DI-06`) exercises real process/transaction/network boundaries without production crash switches. See `BIC-03` for the exact table lock target required to prove mid-transaction rollback *after* initial row insertion.

### 2. Substantive blockers (`changes-requested` before releasing `WP-0003`)

- **`SB-01` — Internal contradiction between `%PDF-2.0` header admission and `PdfPig 0.1.16` `UseLenientParsing=false` ([F1-durable-intake.md](../../../design/F1-durable-intake.md) L37)**:
  - *Evidence*: Step 4 mandates admitting `%PDF-1.0` through `%PDF-1.7` **or `%PDF-2.0`** and opening the PDF with `PdfPig 0.1.16` using `UseLenientParsing=false`. In `UglyToad/PdfPig@a7bb35662bbbf405efddad50aedc9bcdcf515afc` (`src/UglyToad.PdfPig/Parser/FileStructure/FileHeaderParser.cs` L65-L68, L152-L160), `FileHeaderParser.GetHeaderVersionAndResetScanner` rejects any header comment not starting with `"PDF-1."` or `"FDF-1."` by calling `HandleMissingVersion`, which **unconditionally throws `PdfDocumentFormatException` when `UseLenientParsing == false`**. Every `%PDF-2.0` file therefore fails with `422` in strict mode.
  - *Required bounded correction*: Either restrict F1's admitted developer-fixture header versions to `%PDF-1.0` through `%PDF-1.7` (recommended; keeps `UseLenientParsing=false` intact while the byte-0 `%PDF-1.[0-7]` pre-check continues blocking `%FDF-1.x` and leading junk bytes), or explicitly define a narrow `%PDF-2.0` handling rule and add a mandatory `%PDF-2.0` acceptance test without enabling global `UseLenientParsing=true`.
- **`SB-02` — Missing explicit `document.IsEncrypted` rejection, pre-loop `NumberOfPages` guard, and PdfPig `GetPage` side-effect boundaries ([F1-durable-intake.md](../../../design/F1-durable-intake.md) L37, L40, L124)**:
  - *Evidence*: In `UglyToad/PdfPig@a7bb35662bbbf405efddad50aedc9bcdcf515afc` (`PdfDocumentFactory.cs` L516-L519; `EncryptionHandler.cs` L47-L55, L122-L164), PdfPig always injects `string.Empty` into `options.Passwords`. Any PDF encrypted with an owner password and an empty user password opens and parses pages **without throwing `PdfDocumentEncryptedException`**, while `document.IsEncrypted` (`PdfDocument.cs` L151) is `true`. Relying on parse exceptions silently accepts owner-password-encrypted PDFs (`201`), violating Step 4 and `DI-07`. In addition, `document.GetPage(i)` (`PageFactory.cs` L65-L77; `ContentStreamProcessor.cs` L294, L355-L370; `WindowsSystemFontLister.cs` L9-L42) constructs `Letter` glyph objects in memory and scans `C:\Windows\Fonts` when non-embedded TrueType fonts are referenced, while `FlateFilter.cs` L194-L208 swallows `CorruptCompressedDataException` and `FirstPassParser.cs` L550-L560 falls back to `XrefBruteForcer` even under `UseLenientParsing=false`.
  - *Required bounded correction*: Specify in Step 4 and L40/L124 that: (a) immediately after `PdfDocument.Open`, `document.IsEncrypted == true` is rejected with `422`, and `document.NumberOfPages` outside `1..MaxPages` is rejected with `422` *before* looping `GetPage(1..document.NumberOfPages)`; (b) `DI-07` encrypted-PDF checks cover owner-password/empty-user-password encryption (or verify `document.IsEncrypted` rejection directly); (c) *"Do not ... extract/persist text ... or fetch external resources"* prohibits *application* reading/returning/persisting of `Page.Text`/`Letters` while acknowledging PdfPig's internal glyph parsing, local `WindowsSystemFontLister` lookup (synthetic product fixtures must embed or use standard-14 PDF fonts), and `FlateFilter`/`XrefBruteForcer` fallbacks.
- **`SB-03` — Align browser `Submission outcome unknown` state with server `5xx` post-commit uncertainty and `429` retryability ([F1-durable-intake.md](../../../design/F1-durable-intake.md) L38, L60)**:
  - *Evidence*: L38 states that on unexpected infrastructure failure the server returns `5xx` *"and let[s] the client reconcile the key"* (because a DB/network failure right after PostgreSQL WAL commit flush can surface to the API as an exception even though the transaction committed). However, L60 states only that *"A network error or client timeout shows **Submission outcome unknown**, retaining that key."* If the Angular UI treats HTTP `5xx` as a terminal error rather than `Submission outcome unknown`, it fails to offer key reconciliation on the exact server failure path in L38.
  - *Required bounded correction*: Update L60 so HTTP `5xx` responses on `POST /api/documents` also enter **Submission outcome unknown** retaining the `sessionStorage` UUID key for status query / same-key retry, and clarify that `429` retains the pending key for retry without classifying the document as invalid.

### 3. Bounded implementation checks for `WP-0003` (`BIC-01` through `BIC-06`)

1. **`BIC-01` (EF Core projection & FK `Restrict`)**: Project metadata columns explicitly (`Select(...)`) on `GET /api/documents/{documentId}`, `GET /api/submissions/{idempotencyKey}`, and Step 3's initial length/digest check so EF Core never selects `original_artifacts.bytes` (`bytea`) unless serving `/original` or confirming exact bytes after length+`sha256` match. Configure FKs on `original_artifacts` and `processing_jobs` with `DeleteBehavior.Restrict` (not default `Cascade`).
2. **`BIC-02` (Step 1 precedence, Kestrel `413` `ProblemDetails`, and `POST`-only `429` gate)**: Validate `Idempotency-Key` (strict 36-char canonical `D` UUID, `!= Guid.Empty`), `Content-Type` (`application/pdf`), `Content-Encoding` (absent/`identity`), and declared `Content-Length > MaxDocumentBytes` (`413`) before reading the body stream; route Kestrel `BadHttpRequestException` through `ProblemDetails` middleware; scope the 2-permit concurrency limiter (`QueueLimit = 0 -> 429`) strictly to `POST /api/documents` so `GET` reconciliation stays unblocked.
3. **`BIC-03` (Deterministic `DI-05` mid-transaction lock target)**: Lock `processing_jobs` (e.g., `LOCK TABLE processing_jobs IN SHARE MODE`), not `documents`, so FK-ordered inserts deterministically insert `documents` first (`RowExclusiveLock` granted on `documents` in `pg_locks`) and block on `processing_jobs` (`granted = false`) before killing the owned API PID and verifying full rollback across all three tables.
4. **`BIC-04` (`.NET 10.0.403` MTP v2 runner opt-in & `10.0.15` vs `10.0.14` check)**: Include `"test": { "runner": "Microsoft.Testing.Platform" }` in `global.json` and `<OutputType>Exe</OutputType>` on test projects without `Microsoft.NET.Test.Sdk` or `xunit.runner.visualstudio` (`dotnet test --help` on `10.0.403` verified VSTest is otherwise default). Verify clean OOB assembly resolution for `EF Core 10.0.15` on installed `10.0.14` shared runtimes (`dotnet-ef 10.0.15` `.nupkg` was verified read-only to use `net8.0` with `rollForward: "Major"`).
5. **`BIC-05` (Worktree-local Playwright/test paths & host IPv6 npm fallback)**: Set `PLAYWRIGHT_BROWSERS_PATH` inside `.local/` if Playwright browsers are fetched, route or `.gitignore` `playwright-report/`, `test-results/`, and `coverage/`, and note `--dns-result-order=ipv4first` if `npm` hits the dual-stack IPv6 timeout observed against `registry.npmjs.org`.
6. **`BIC-06` (PostgreSQL `18.7` binary archive & runtime privileges)**: Record exact EDB/PostgreSQL `18.7` zip URL and SHA-256, initialize `.local/postgres-data` bound solely to `127.0.0.1` (`55432` implementer / `55433` reviewer) with `scram-sha-256`, assert `fsync=on`, `full_page_writes=on`, `synchronous_commit=on`, and restrict runtime DB credentials to `INSERT, SELECT` on the three `F1` tables (migrations run under separate schema credentials).
