## Decisions and rationale

1. **Per-page normal + fallback projection units with parent completion marker (`F4-BIC-02`, `F4-BIC-05`):**
   - `ArchiveMachineProjector` emits `archive_result_projections` (`unit_count >= 0`, deterministic `projection_sha256`) plus at most `2` units per physical page (`page` for recognized blocks and `\t`-joined table cells; `page_fallback` when `<FORK>` is missing or `TableHasNonCellTextOrUnclosedTag` detects `<caption>`/stray non-cell text/unclosed tags/empty rows) or `1` `document_fallback` unit (`page_number = NULL`) when `<PAGE>` markers are missing/mismatched. `\0` (`U+0000`) is replaced with `U+FFFD` without length truncation while leaving `extraction_results.raw_output_bytes` untouched.
2. **Startup readiness, `23505` competing-initializer reconciliation, & coordinator clarifications (`F4-BIC-05`, `F4-BIC-06`):**
   - By default, `ArchiveStartupHostedService.StartingAsync` executes bounded `result_id`-batched integrity verification (recomputing `projection_sha256` without reading `raw_output_bytes` for already-projected rows) and one-result-at-a-time backfill (`LocalOcr:Enabled=false`) **before** Kestrel begins listening; no HTTP status is claimed before a listener exists. If an existing projection conflicts, the host still starts listening with readiness set to `Conflict` (mutating nothing) so `GET /api/archive` serves `503 archive_projection_conflict` while `/api/documents` and review endpoints remain operational; while listening, deferred/in-progress initialization or unprojected rows with catch-up disabled serve `503 archive_not_ready` (`Retry-After: 1`).
   - `ArchiveCursor` validates Base64Url format (`<= 256` chars), JSON shape, cursor version (`archive-cursor/1`), UTC microsecond bounds, lowercase UUID, and `(source, terms)` SHA-256 scope binding (`400 cursor_query_mismatch`); as clarified by coordinator, it is a structural/query-binding guard rather than cryptographic HMAC authentication.
3. **Preserving `eledgercare_f4_author_seed_f3` while proving real forward migration (`F4-05`):**
   - Because the preparation seed digest (`76e7970b...`) covers the 3-row `__ef_migrations_history` table alongside the 8 core tables, cloning `eledgercare_f4_author_migrated` from `TEMPLATE eledgercare_f4_author_seed_f3` (verified at `76e7970b...` prior to migration) and running `prepare-database.ps1 -Database eledgercare_f4_author_migrated` proves real `dotnet-ef` forward migration (`ad4f44bc...` core 8-table data SHA-256 unchanged across migration, backfill, and PG+API restart) while keeping `eledgercare_f4_author_seed_f3` itself 100% untouched at `76e7970b...`.
