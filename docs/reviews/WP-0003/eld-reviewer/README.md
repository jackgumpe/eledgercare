### Question 2: Added `startxref`-Target Precondition (`PdfPigAdmission.cs:111-145`)

- **What Changed vs Literal Design**: When `eld-implementer` tested `startxref` corruption (`0` or out-of-range offset), `PdfPig 0.1.16` recovered the object graph via `XrefBruteForcer` even with `ParsingOptions { UseLenientParsing = false }`. The author added `StartXrefAddressesCrossReference` (`src/ELedgerCare.Infrastructure/Pdf/PdfPigAdmission.cs:111-145`), checking that the final `startxref` byte offset within the trailing 2 KiB window addresses either `"xref"` followed by a PDF delimiter/whitespace or `<objNum> <ws> <genNum> <ws> obj` followed by a PDF delimiter/whitespace.
- **Correctness & False-Rejection Assessment**:
  - Under ISO 32000-1:2008 (PDF 1.0–1.7), every conforming cross-reference section addressed by `startxref` (including incremental updates and Annex F linearized first-page cross-reference sections) begins either with the `xref` keyword (§7.5.4) or with an indirect cross-reference stream object `<N> <G> obj << /Type /XRef ... >>` (§7.5.8).
  - Independent reviewer probes (`pdf-admission-edge-probes.json`) verified that valid **PDF 1.5 Flate-compressed `/Type /XRef` streams** (`620` bytes, no `xref` table), **PDF 1.4 incremental updates** (`1,047` bytes, two `startxref` sections), and **valid PDFs with trailing PDF whitespace (`\r`, `\n`, space, `\0`) after `%%EOF`** are all **admitted** (`IsAdmitted = true`), while `startxref 0` is **rejected** (`InvalidCrossReference`).
  - The 10-digit integer parser (`ReadPositiveInt`, `lines 150-166`) accommodates offsets up to `9,999,999,999` bytes, well above the `10,485,760`-byte F1 size ceiling; only non-standard >10-digit zero-padded offsets or >~2 KiB post-`%%EOF` garbage would fail the scan.
- **Disposition**: **Sound and accepted**, with negligible false-rejection risk on conforming PDF 1.0–1.7 documents within the F1 admission envelope.

### Question 3: Known `PdfPig` Recovery Limitation & Precision of Malformed-PDF Claims

- **Technical Scope of the Limitation**:
  - Because `PdfPig 0.1.16` still invokes `XrefBruteForcer` when `UseLenientParsing = false`, two narrow classes of cross-reference corruption remain recoverable and admitted:
    1. **Shifted per-object `xref` byte offsets** behind a `startxref` that validly points to `xref` (pinned explicitly by author test `PdfPigAdmissionTests.cs:210-226`).
    2. **A `startxref` offset pointing to an ordinary non-`/XRef` `<N> <G> obj` header** (e.g., `1 0 obj`), empirically demonstrated by reviewer probe (`startXrefPointingToNonXrefObjectHeader.isAdmitted = true`), because `StartXrefAddressesCrossReference` checks for `<int> <ws> <int> <ws> obj` syntax without parsing the stream dictionary for `/Type /XRef`.
  - Additionally, `StartXrefAddressesCrossReference` does not verify that only whitespace separates the parsed `startxref` integer from `%%EOF` prior to `PdfDocument.Open`.
- **Precision of Documentation & Design Alignment**:
  - Accepted design `docs/design/F1-durable-intake.md:40` explicitly anticipated this boundary: *"It is a pragmatic structural/resource gate, not a complete PDF conformance validator; R&D source evidence notes PdfPig caveats such as XrefBruteForcer recovery despite strict parsing."*
  - Both `docs/product/F1-durable-intake-implementation.md:31-38` and `WP-0003 / 001` (`Decisions 2–3`, `Risks`) state this limitation accurately without overclaiming full ISO 32000-1 xref validation, and appropriately avoid writing a custom PDF parser in F1.
- **Disposition**: **Accepted as accurately bounded and honestly documented.**
