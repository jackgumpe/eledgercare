## Customer outcome and limits

A local operator opens an existing completed extraction, compares its original pages with five work-order fields, records corrections or unknown values, saves a draft or explicitly reviewed revision, and reopens the same revision after restart. The original PDF, raw model result, provenance and extraction-attempt history remain untouched. An extraction completion and an operator review are different facts.

One explicit profile, `maintenance-work-order/1`, covers five fields: `work_order_id` (64 characters), `property_name` (200), `building_unit` (120), `requested_date` (64), `issue_and_resolution` (4000). The date remains printed text in this slice; no date, identifier, monetary or unit normalization, fuzzy correction, field inference from expected fixtures, LLM judge or automatic approval. Limits count .NET UTF-16 code units consistently; reject unpaired surrogates/NUL and invalid/control text except ordinary line breaks/tabs in the multiline narrative. Valid printable Unicode and leading identifier zeros remain exact. Values composed only of whitespace are empty. No new document formats, table-cell editing, business accounting integration, search, authentication system or deployment. Existing admitted synthetic one-to-three-page profile remains the execution boundary. User explicitly chooses to start a work-order review; absence of this choice does not classify arbitrary invoices as work orders.

## Small production suggestion boundary

F2 exposes native text blocks/tables rather than business fields. Add a self-contained production `WorkOrderReviewSuggestions` boundary using only the stored raw result and the safe display parser. It must not reference/import/invoke `qualification/`, `research/`, `evaluation/`, fixture manifests or expected values. This is a five-label convenience for one declared profile, not a claim of general mapping quality. Keep mapper identity `work-order-suggestions/1` and field schema version in saved review provenance.

Freeze this conservative first policy before implementation:

- Exact labels after outer whitespace/one trailing colon removal only: `Work Order ID`, `Property`, `Building / Unit`, `Requested Date`, and `REPORTED SYMPTOM & TECHNICIAN RESOLUTION SUMMARY` map respectively to the five fields. No alias list expansion during this packet.
- An inline text block consisting of one exact label followed by a colon and nonempty value may suggest the exact remainder. Otherwise a standalone exact label may use the immediately following nonempty text block on the same page, provided it is not itself a recognized label, title, footer or table. No skipping across intervening blocks, pages or headings. The narrative heading may be a title block, but its value must be the immediate text block. More than one candidate for a field is ambiguous even if values repeat: produce unknown and expose the competing source references, never choose silently.
- A plain table row containing an exact known label and a single adjacent nonempty value cell may produce a suggestion only if the row has exactly two simple cells. Reject spanning/ambiguous rows and unsupported structures. Table-specific improvement research stays independent; this product policy has no broad table/header mapping.
- Enforce field limits and safe text checks before suggesting. Unsupported, missing, ambiguous or oversized candidates remain null/unknown. Do not truncate a candidate into a plausible value.
- Every suggestion retains exact result ID/raw SHA256, page number, zero-based block ordinal and optional table row/column, plus the exact source quote. These are positions in a versioned parse of this immutable raw result, not PDF bounding-box accuracy claims. Validate source identities server-side; clients cannot submit invented provenance. UI offers source-page navigation and the extracted quote for verification. No confidence percentages.

Initial suggestions are unreviewed. User edits are distinct human values; source references may be retained as the evidence the operator consulted, never falsely as machine output. The immutable machine candidate/quote remains visible beside the current human value and is persisted in the first review snapshot. Later reloads/edits reuse that snapshot, so a future suggestion algorithm cannot silently change historical review provenance.

## Review state and persistence model

Each saved revision binds one document, its accepted extraction result, input/raw digests, field schema and suggestion version. Revisions are append-only, ordered by server-generated revision number, with server timestamp, previous revision number, client operation UUID and request digest. A small mutable review-head row identifies the current revision. Use a forward EF migration, existing PostgreSQL only, no generic event-store/broker/repository framework. Preserve all existing F1/F2 rows and constraints; never update original/raw/result bytes.

Revision state is `draft` or `reviewed`. Each field has a decision `unreviewed`, `accepted`, `edited`, or `unknown`, and a nullable human value. `accepted` requires a nonempty original machine suggestion and exact equality to it. `edited` requires a valid nonempty human value and is visibly human-authored, even if entered without a machine candidate. `unknown` has no asserted value, retains the original candidate separately, and requires an explicit operator decision; optional bounded reason (500 characters). `unreviewed` may hold a draft value but cannot complete review. An explicit `reviewed` save requires all five decisions to be accepted/edited/unknown, with a clear UI summary of unknown fields and affirmative confirmation. A reviewed revision with unknowns is valid and displayed as such; it does not certify factual completeness. Saving further edits creates a new draft revision; an older reviewed revision remains historical, not the current review's approval. No overwriting or deleting revisions.

Record an optional self-reported operator display label (80 characters), and show that this is a local unauthenticated review. Do not invent authenticated identity or legal approval claims. Server timestamps/IDs and provenance remain factual even when the display label is absent. Review completion is an operator action, not a medical/financial/compliance certification.

Runtime role gets only needed SELECT/INSERT on revision data, and minimal SELECT/INSERT/UPDATE on review heads, without UPDATE/DELETE on revisions or extraction results. Foreign keys bind document/result consistently with deletion restricted. Enforce unique operation identity and unique revision number per document/result. All invariants must survive direct concurrent API calls, not rely on disabled UI buttons. Cap one request at32KiB and revision count at128 per result; refuse further saves explicitly without deleting history. History responses contain bounded summaries; a selected revision endpoint returns its field snapshot.

## API and conflict semantics

Freeze concrete response DTOs in implementation within these semantics:

| Boundary | Required behavior |
| --- | --- |
| GET `/api/documents/{documentId}/review` | Existing current revision plus machine snapshot/history summaries, or an explicitly unsaved preview at revision0 for a completed supported extraction. Pure read: no saved revision, job or inference side effect. |
| GET `/api/documents/{documentId}/review/revisions/{revisionNumber}` | Exact historical saved revision bound to this document/result; valid missing revision404; malformed identifiers400. |
| POST `/api/documents/{documentId}/review/revisions` | Required UUID Idempotency-Key, accepted resultId, expectedRevision (0 on first save), draft/reviewed state and exactly the five fields/decisions. Validate sizes/types/values; server owns source identity/snapshot/timestamps. New save201 after commit, exact replay200. |
| GET `/api/documents/{documentId}/preview` | Same original committed PDF bytes/digest, controlled inline filename and application/pdf/nosniff headers for local source viewing. Original attachment endpoint remains unchanged. No caller-provided path/URL, fetch or render service. |

A short PostgreSQL transaction atomically checks the expected revision, inserts the immutable snapshot and advances the head. A lost response may follow commit: the same operation key and same validated request must replay the original committed revision even if a later revision now exists. Same key with different content returns409; a different operation with stale expectedRevision returns409 with current revision reference, preserves the operator's unsaved edits in UI memory and requires explicit reload/reconciliation. Never silently overwrite or automatically merge edits. Check idempotent replay before stale-head rejection. Specify deterministic request-digest semantics, including field order and server-owned values, in the implementation contract/tests. Invalid/absent/noncompleted result, wrong document/result binding, unsupported profile or field decisions must not create a review. No long transaction spans browser interaction.

The browser distinguishes unsaved edits, saved draft, reviewed (including unknown count), saving and uncertain save outcome. On transport failure/5xx, retain operation key/body in memory and provide same-key reconciliation/retry; do not claim failure or mint a new operation automatically. Keep document/revision references in URLs; no document contents/review values in browser persistent storage. Refresh can discard unsaved memory with an honest warning; acknowledged saved revisions survive restart. Reopening or saving never calls OCR.
